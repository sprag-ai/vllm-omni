# Multimodal Choice, Noul and Score API (prototype)

`--choice-bundle PATH` enables `POST /v1/systemone` in the existing vLLM-Omni HTTP server. It accepts TypeSafe-style Choice, Noul and Score questions and returns named answers directly, without an OpenAI chat envelope or public A/B/C labels. The existing `--decision-bundle` mode is unchanged; the two flags are mutually exclusive.

```sh
vllm serve /models/qwen3 --omni --choice-bundle /models/choice \
  --served-model-name spev --max-num-seqs 8 \
  --max-num-batched-tokens 16384 --api-key "$SPEV_API_KEY"
```

The bundle contains `choice.json`, `adapter/adapter_config.json`, `adapter/adapter_model.safetensors`, and `calibration.json`. `choice.json` records a resolved model name and SHA256 hashes of the other three files. Calibration records the matching adapter SHA256, a positive temperature, and scorer `vllm-full-sequence-choice-v1`. A temperature fitted using a different runtime must not be relabeled as serving calibration. An identity temperature is useful for engineering tests but is not fitted calibration.

## Native request

```json
{
  "model": "spev",
  "state": "I was charged twice. Please refund the duplicate payment.",
  "questions": {
    "department": {
      "type": "choice",
      "instructions": "Which team should handle this?",
      "criteria": {
        "billing": "Payments and refunds",
        "technical": "Software issues",
        "sales": "New purchases"
      }
    }
  }
}
```

Send this JSON to `/v1/systemone` with `Authorization: Bearer <key>` and `Content-Type: application/json`. The host must route this endpoint to the Choice server. Adding the model-server route does not add a route to an external gateway; the existing Sprag gateway needs a separate reviewed change before this is available at its public host.

`state` and `instructions` accept strings, objects or arrays. Criterion descriptions also accept null. Question IDs are echoed in `answers` and are never included in model prompts. Criteria names are semantic labels, not one-token aliases.

## Native response

Illustrative values, not a measured model response:

```json
{
  "model": "spev-choice-revision",
  "answers": {
    "department": {
      "type": "choice",
      "choice": "billing",
      "probabilities": {"billing": 0.9, "technical": 0.07, "sales": 0.03},
      "confidence": 0.85
    }
  },
  "usage": {"input_tokens": 123, "output_tokens": 0}
}
```

Probabilities come from a softmax over complete named-target log likelihoods, divided by the bundle temperature. They are not numbers generated by the model. Confidence is `(max_probability - 1/N) / (1 - 1/N)`. Usage counts logical input prompt tokens once per question; scoring repeats the prompt for each candidate, so this is not a measure of total GPU work. The internal discarded sample is not a returned output token.

## Noul and Score

Questions can mix all three primitives in one request. Noul accepts an assertion and optional `criteria` with both `"true"` and `"false"` descriptions. It returns `{"type":"noul","noul":0.8}`: a probability, not a Boolean. Score accepts an ordered array of 2–10 descriptions. It returns the expected zero-based level, a `legend`, a probability per level, and spread-based confidence.

```json
{
  "model": "spev",
  "state": "Please refund the duplicate charge.",
  "questions": {
    "refund": {"type":"noul", "instructions":"Is the caller requesting a refund?"},
    "urgency": {
      "type":"score", "instructions":"Rate the urgency.",
      "criteria":["Routine", "Urgent", "Emergency"]
    }
  }
}
```

The adapter converts Noul into named `true`/`false` candidates and Score into zero-based named candidates, then scores their complete JSON targets. Score is `sum(i * p[i])`. Its confidence is `max(0, 1 - spread/even_spread)`, where `spread = sum(p[i] * abs(i - mode))`, ties select the lowest mode, and `even_spread = sum(abs(i - (N-1)/2))/N`. These are computed from likelihoods, not generated numerical text. This matches the response shapes and formulas; it does not establish equivalence to JEV's model or scoring internals.

The bundle temperature is retained for text/audio Choice. New primitives and any request containing visual evidence use identity temperature. They have not been calibrated or accuracy-benchmarked by the existing audio evaluation.

## Audio extension

SPEV optionally accepts top-level `input_audio: {"data": "<base64 bytes>", "format": "<container hint>"}` alongside `state` and `questions`. This is a SPEV extension: the inspected TypeSafe reference does not define native audio transport. The shared vLLM decoder determines supported containers; no adapter-specific WAV/FLAC allowlist is used. No URL fetching is supported. Existing decoder size, channel, rate and duration bounds apply.

## Image and video extensions

SPEV also accepts optional `input_image` and `input_video`, each with the same `{ "data": "<base64 bytes>", "format": "<container hint>" }` shape. One image, one video and one audio input may accompany the shared state. The native vLLM image and video loaders decode the bytes; the format is informational, not a container allowlist. URLs and local paths are not accepted. Each inline file is at most 12 MiB decoded and the existing aggregate HTTP body limit also applies.

Video uses the native loader's 32-frame sampling default and preserves its temporal metadata. It supplies visual frames only; provide the soundtrack separately as `input_audio` when needed. Separate audio and video are shared evidence, not synchronized audio-in-video tokens. Frames and images pass through the Qwen vision processor and deepstack encoder. All expanded media tokens count toward the 8192-token context; oversized inputs are rejected before candidate scheduling.

## Validation and limits

Pydantic validates requests at the HTTP boundary and rejects unknown fields before inference. Choice supports 2–255 criteria, Noul has two outcomes, and Score supports 2–10 ordered levels. There are at most 16 questions and 255 total candidate outcomes per request. Text across state, question IDs, instructions and criteria is limited to 65,536 characters and 4,096 structure nodes, independently of the audio upload limit. Streaming and free-form generation parameters are rejected. These limits and the audio extension mean this is not a claim of complete TypeSafe API compatibility.

Invalid requests return 422 with field locations but no submitted input echoed in errors. Authentication uses the existing vLLM middleware. Full admission returns 429 with `Retry-After: 1`; an unavailable engine returns 503. Unexpected per-request failures return 500 without disabling a healthy engine. `/load` reports admitted requests on either route, including work whose HTTP waiter disconnected. Request admission stays occupied until outstanding work completes, including after a disconnected HTTP waiter. Shutdown drains tracked requests.

`/v1/chat/completions` remains an explicitly labeled compatibility wrapper: one user message with one text part containing a JSON `{"state": ..., "questions": ...}` object, and optionally one part for each media type: `input_audio`, `input_image`, `input_video`, each with its corresponding named payload field. Its `message.content` is the entire native response serialized as JSON. TypeSafe clients should use `/v1/systemone` directly.

## Runtime scope

This uses AsyncLLM and the native Qwen3-Omni Thinker with the trained FP32 Q/V adapter. It scores each complete named JSON target, including the end marker, through prompt log probabilities. Prompt preparation runs off the event loop. Caller angle brackets are JSON-escaped, preserving their values without allowing literal special tokens to become conversation or audio markers. This prevents structural token injection; it is not a guarantee against semantic prompt injection. The shared prefix is tokenized once per question and submitted as token IDs. The 8192-token budget includes expanded audio, image and video placeholders, each target and the discarded sample, and is checked before candidate scheduling. Candidates can batch through the scheduler; each candidate still repeats model prefill and media processing. This is more work than the old fixed three-class early-exit policy and inherits no latency claim from it.

Settings are BF16 base, FP32 adapter updates, eager execution, TP/PP=1, seed17, an 8192-token context and invariant kernels. Unsupported explicit CLI/config options are rejected rather than ignored. The candidate requires runtime-specific calibration and target-hardware validation before rollout. No production deployment is part of this change.
