# Named Choice API (prototype)

`--choice-bundle PATH` enables `POST /v1/systemone` in the existing vLLM-Omni HTTP server. It accepts TypeSafe-style Choice questions and returns named answers directly, without an OpenAI chat envelope or public A/B/C labels. The existing `--decision-bundle` mode is unchanged; the two flags are mutually exclusive.

```sh
vllm serve /models/qwen3 --omni --choice-bundle /models/choice \
  --served-model-name spev --max-num-seqs 8 \
  --max-num-batched-tokens 16384 --api-key "$SPEV_API_KEY"
```

The bundle contains `choice.json`, `adapter/adapter_config.json`, `adapter/adapter_model.safetensors`, and `calibration.json`. `choice.json` records a resolved model name and SHA256 hashes of the other three files. Calibration records the matching adapter SHA256, a positive temperature, and scorer `vllm-full-sequence-choice-v1`. A temperature fitted using a different runtime must not be relabeled as serving calibration. An identity temperature is useful for engineering tests but is not fitted calibration.

## Native request

```json
{
  "model": "spev",
  "state": "I was charged twice. Please refund the duplicate payment.",
  "questions": {
    "department": {
      "type": "choice",
      "instructions": "Which team should handle this?",
      "criteria": {
        "billing": "Payments and refunds",
        "technical": "Software issues",
        "sales": "New purchases"
      }
    }
  }
}
```

Send this JSON to `/v1/systemone` with `Authorization: Bearer <key>` and `Content-Type: application/json`. The host must route this endpoint to the Choice server. Adding the model-server route does not add a route to an external gateway; the existing Sprag gateway needs a separate reviewed change before this is available at its public host.

`state` and `instructions` accept strings, objects or arrays. Criterion descriptions also accept null. Question IDs are echoed in `answers` and are never included in model prompts. Criteria names are semantic labels, not one-token aliases.

## Native response

Illustrative values, not a measured model response:

```json
{
  "model": "spev-choice-revision",
  "answers": {
    "department": {
      "type": "choice",
      "choice": "billing",
      "probabilities": {"billing": 0.9, "technical": 0.07, "sales": 0.03},
      "confidence": 0.85
    }
  },
  "usage": {"input_tokens": 123, "output_tokens": 0}
}
```

Probabilities come from a softmax over complete named-target log likelihoods, divided by the bundle temperature. They are not numbers generated by the model. Confidence is `(max_probability - 1/N) / (1 - 1/N)`. Usage counts logical input prompt tokens once per question; scoring repeats the prompt for each candidate, so this is not a measure of total GPU work. The internal discarded sample is not a returned output token.

## Audio extension

SPEV optionally accepts top-level `input_audio: {"data": "<base64 bytes>", "format": "<container hint>"}` alongside `state` and `questions`. This is a SPEV extension: the inspected TypeSafe reference does not define native audio transport. The shared vLLM decoder determines supported containers; no adapter-specific WAV/FLAC allowlist is used. No URL fetching is supported. Existing decoder size, channel, rate and duration bounds apply.

## Validation and limits

Pydantic validates requests at the HTTP boundary and rejects unknown fields before inference. This prototype implements **Choice only**, with 2–255 criteria per question, at most 16 questions, and at most 255 total criteria per request. Text across state, question IDs, instructions and criteria is limited to 65,536 characters and 4,096 structure nodes, independently of the audio upload limit. Noul, Score, streaming and free-form generation parameters are rejected. These limits and the audio extension mean this is not a claim of complete TypeSafe API compatibility.

Invalid requests return 422 with field locations but no submitted input echoed in errors. Authentication uses the existing vLLM middleware. Full admission returns 429 with `Retry-After: 1`; an unavailable engine returns 503. Unexpected per-request failures return 500 without disabling a healthy engine. `/load` reports admitted requests on either route, including work whose HTTP waiter disconnected. Request admission stays occupied until outstanding work completes, including after a disconnected HTTP waiter. Shutdown drains tracked requests.

`/v1/chat/completions` remains an explicitly labeled compatibility wrapper: one user message with one text part containing a JSON `{"state": ..., "questions": ...}` object, and optionally one audio part. Its `message.content` is the entire native response serialized as JSON. TypeSafe clients should use `/v1/systemone` directly.

## Runtime scope

This uses AsyncLLM and the native Qwen3-Omni Thinker with the trained FP32 Q/V adapter. It scores each complete named JSON target, including the end marker, through prompt log probabilities. Prompt preparation runs off the event loop. Caller angle brackets are JSON-escaped, preserving their values without allowing literal special tokens to become conversation or audio markers. This prevents structural token injection; it is not a guarantee against semantic prompt injection. The shared prefix is tokenized once per question and submitted as token IDs. The 8192-token budget includes expanded audio placeholders, each target and the discarded sample, and is checked before candidate scheduling. Candidates can batch through the scheduler; each candidate still repeats model prefill and audio processing. This is more work than the old fixed three-class early-exit policy and inherits no latency claim from it.

Settings are BF16 base, FP32 adapter updates, eager execution, TP/PP=1, seed17, an 8192-token context and invariant kernels. Unsupported explicit CLI/config options are rejected rather than ignored. The candidate requires runtime-specific calibration and target-hardware validation before rollout. No production deployment is part of this change.
